# 6. Data

If you are only generating a policy checklist refer to the [Policy Checklist Data](https://healthysustainablecities.github.io/global-indicators/6.-Data#policy-checklist-data)      

When configuring a new study region you will need some input data.  At minimum, that is a population grid, an excerpt from OpenStreetMap, and a study region boundary — either an administrative boundary, or an urban centre from the Global Human Settlements Urban Centres Database.  Everything else is optional: custom boundaries to aggregate results for, GTFS transit feed data, your own destinations or open space, or a completed policy checklist.


**There is no required folder structure.**  Data paths are configured relative to the `process/data` folder; beyond that, organise your data however suits your project.  No input data is distributed with the software apart from the bundled example, so these are folders you create.

Earlier versions shipped a folder for each kind of data — `population_grids`, `region_boundaries`, `transit_feeds`, `urban_regions`; however, we found that splitting one city across several folders could make it harder to see what a study region is made of, and harder to move or share it.

We now recommend keeping each study region’s data together in a folder of its own, with its configuration file alongside it.  The bundled example does exactly this — everything for Las Palmas de Gran Canaria is in `process/data/examples/ES_Las_Palmas_2025/`, its configuration file in a `configuration` sub-folder there — so the whole region can be moved, shared or archived as one thing.  [Detailed setup](https://healthysustainablecities.github.io/global-indicators/5.-Detailed-Setup) explains how configuration files are found in that location as well as in `process/configuration/regions`.

The [bundled example](https://github.com/healthysustainablecities/global-indicators/tree/main/process/data/examples/ES_Las_Palmas_2025) is a good pattern to copy, but it is only a suggestion — nothing in the software requires it.  Data shared between several study regions is a reasonable exception: a country-wide OpenStreetMap extract or a population grid covering a whole region can sit wherever makes sense, with each study region’s configuration pointing at it.


The bundled example provides a worked instance of each of the following, apart from a completed policy checklist.

Each section names its dataset with a `data` setting, holding a path relative to `process/data`.  In the bundled example, for instance, the population data is configured as `data: examples/ES_Las_Palmas_2025/population/ghsl_100m`.

Earlier versions used `data_dir` for the `population`, `urban_region` and `OpenStreetMap` sections.  That key is still accepted, so existing configuration files continue to work, but `data` is preferred and is what the other sections have always used.  (The `gtfs` section’s `data_dir` is a different thing — a root folder for feeds, rather than a path to a dataset — and is unchanged.)

A dataset path may select a layer within a geopackage by appending its name after a colon, and may filter features with an OGR `-where` clause.  This is how an urban centre is selected from the Urban Centre Database, replacing the deprecated `urban_query` parameter.


OpenStreetMap data are used to represent features of interest within regions of interest.

This can be retrieved in .pbf (recommended; smaller file size) or .osm format from sites including:

- https://download.geofabrik.de/
- http://download.openstreetmap.fr/extracts/
- https://planet.openstreetmap.org/pbf/  (whole of planet data archives; very large file sizes, but can be useful for retrieving historical data)

It is recommended that a suffix to indicate the publication date is added to the name of downloaded files as a record of the time point at which the excerpt is considered representative of the region of interest e.g. "las_palmas-latest.osm_20230210.pbf" or "oceania_yyyymmdd.pbf" where yyyy is the year, mm is the 2-digit numerical month, and dd is the 2-digit numerical day date_.

The main considerations are that the excerpt is as small as possible while ensuring that it has complete coverage of the region(s) of interest (and about 1600 metres additional beyond the boundary, or as otherwise configured).  Using a smaller rather than a larger file will speed up processing.

For example, for a project considering multiple cities in Spain, the researchers could download an excerpt for the country of [Spain](https://download.geofabrik.de/europe/spain.html) or for specific sub-regions like [Catalunya](https://download.geofabrik.de/europe/spain/cataluna.html) as required to ensure that the region of interest is encompassed within the extract.  Using the example of Spain, which also contains regions outside Europe, if sourcing from Geofabrik as the example links above, it is worth noting that the excerpts are grouped by continent so some care should be taken.  For example, [Las Palmas de Gran Canaria](https://download.geofabrik.de/africa/canary-islands.html) are found under the Canary Islands in Africa on Geofabrik, or a smaller PBF specifically for [Las Palmas](https://download.openstreetmap.fr/extracts/africa/spain/canarias/) can be retrieved from download.openstreetmap.fr under 'africa/spain/canarias'.  Our software provides example data for Las Palmas, and to reduce file size we prepared a clipped portion of the data around this city using only the minimum area required.


Population grid or vector data are used to represent the population distribution within regions of interest.

We recommend usage and configuration of the most reliable population data available for your chosen study region and time point.  The latest release of the [Global Human Settlements Layer population data](https://ghsl.jrc.ec.europa.eu/download.php?ds=pop) using Mollweide (equal areas, 100m) projection may be a good option for modelled population distribution estimates, in the absence of up-to-date or high-resolution official data.  *note: take care when retrieving the GHSL population data to select the correct Epoch for your analysis!*

Optionally, official population data can be used if this is judged to be more accurate or meaningful for your city's analysis and interpretation of results by your intended audience.  For example, to use the official 1km Australian population grid for 2021 (instead of the 100m grid estimates from the GHSL-POP r2022a dataset for 2020 or 2025), this could be specified as per the following code block:

```
population:
    name: "Australian Population Grid 2021 (ABS, 2023)"
    data: AU_Melbourne_2021/population/Australian_Population_Grid_2021_in_TIFF_format
    data_type: raster:Int64
    resolution: 1km
    raster_band: 1
    raster_nodata: 
    pop_min_threshold: 5
    crs_name: GDA94 / Australian Albers
    crs_standard: EPSG
    crs_srid: 3577
    source_url: https://www.abs.gov.au/statistics/people/population/regional-population/2021/GEOTIFF.zip
    year_published: 2022
    year_target: 2021
    date_acquired: 20230302
    licence: CC BY 4.0
    citation: "Australian Bureau of Statistics (2022), Australian Population Grid 2021. https://www.abs.gov.au/statistics/people/population/regional-population/2021"
```

In the above vector data example, this contains multiple fields with estimates by age group which opens up additional possibilities for analysis of indicators for specific population sub-groups (in this case, using age).   To do this, one could modify the `vector_population_data_field` to the field containing the population of interest, e.g.
```
    vector_population_data_field: P_15_64
```
In this way, age-specific indicators could be calculated and compared.  Indicators based on overall population density use the estimates from the `population_denominator` field; hence, if you are interested in the overall population for your indicators the data_field and the denominator should share the same value.

Choice of the population data grid is an important methodological choice for analysts as it determines the resolution at which results are output (for example a choice between 100m estimated population, or 1000m official population statistic, or administrative areas of varying dimensions).  As such, it is good to know that this is an option available to ensure your indicator results serve their intended purpose and audience.


Region boundary data are used to identify the study region(s) of interest.  These may be retrievable from a government open data portal, or the UN OCHA [Humanitarian Data Exchange](https://data.humdata.org/). 

Additional custom region boundaries can be used to summarise indicator results for your own areas of interest — administrative boundaries, statistical areas, neighbourhoods, catchments, or individual buildings.  These are configured under `custom_aggregations`, and two worked examples are included with the example study region.  See [Custom aggregation](https://healthysustainablecities.github.io/global-indicators/Custom-aggregation) for what each option does and how to use them.



Restricting analysis to a specific region of a city is a powerful way to ensure results are meaningful.  In particular, walkability and related measures have been designed for urban settings where the expectation of having access to services and amenities may be reasonable, in contrast to rural areas that may still be located within the greater metropolitan administrative boundaries of cities but which arguably should be excluded from urban walkability analyses.  Official data on urban areas (for example using the Australian Bureau of Statistics' Sections of State datasets, for Australian cities) can be configured in this way. An appropriate release of the Global Human Settlements Layer Urban Centres Database (e.g. [r2024A](https://human-settlement.emergency.copernicus.eu/ghs_ucdb_2024.php)) can be downloaded and by exploring the attributes in a desktop GIS like QGIS, a query can be determined for identifying the appropriate urban area.

An urban region is an ordinary spatial dataset: the area of interest within it is selected with a `-where` query, exactly as for any other dataset, and a layer within a geopackage is selected by appending its name after a colon.  The restriction takes effect when `study_region_boundary` is configured with `urban_intersection: true`, which intersects the study region boundary with the urban region selected here.

## Examples

**Melbourne, using the ABS Sections of State**

Australia's Sections of State classify areas as Major Urban, Other Urban, Bounded Locality or Rural Balance.  Selecting the two urban classes restricts the analysis to the urban portion of the Greater Melbourne administrative boundary.  The dataset is distributed as a zipped shapefile, which can be read in place without being unpacked first:

```yaml
urban_region:
  ## name for the urban region data
  name: ABS ASGS Sections of State 2025
  ## path relative to process/data, with the urban sections selected by query
  data: "AU/SOS_2021_AUST_GDA2020_SHP.zip -where \"SOS_NAME21 IN ('Major Urban','Other Urban')\""
  ## licence, e.g. CC BY 4.0
  licence: CC BY 4.0
  ## citation
  citation: "Australian Bureau of Statistics (2021). Section of State - 2021 - Shapefile. Australian Statistical Geography Standard (ASGS) Edition 3. https://www.abs.gov.au/statistics/standards/australian-statistical-geography-standard-asgs-edition-3/jul2021-jun2026"
```

**Las Palmas de Gran Canaria, using the GHS Urban Centre Database**

The bundled example ships a small excerpt of the R2024A database.  It is a scaled down replica of the distributed geopackage — same layer name, same attributes, one feature instead of all of them — so it is configured exactly as the full database would be, with the urban centre selected by query:

```yaml
urban_region:
  ## name for the urban region data
  name: "GHS Urban Centre Database R2024A (European Commission JRC, 2024; Las Palmas de Gran Canaria only)"
  ## path relative to process/data, selecting a layer within the geopackage
  ## and then the urban centre of interest within that layer
  data: "examples/ES_Las_Palmas_2025/urban_region/GHS_UCDB_R2024A_Las_Palmas.gpkg:GHS_UCDB_THEME_GENERAL_CHARACTERISTICS_GLOBE_R2024A -where \"GC_UCN_MAI_2025='Las Palmas de Gran Canaria' AND GC_CNT_GAD_2025='Spain'\""
  ## licence, e.g. CC BY 4.0
  licence: CC BY 4.0
  ## citation
  citation: "Pesaresi, M., Schiavina, M., Politis, P., Freire, S., Krasnodębska, K., Uhl, J. H., … Kemper, T. (2024). Advances on the Global Human Settlement Layer by joint assessment of Earth Observation and population survey data. International Journal of Digital Earth, 17(1)."
```

To configure your own city, [download the full database](https://human-settlement.emergency.copernicus.eu/ghs_ucdb_2024.php) and change the path before the colon; the layer name and the shape of the query stay the same:

```yaml
  data: "urban_regions/GHS_UCDB_GLOBE_R2024A_V1_0/GHS_UCDB_GLOBE_R2024A.gpkg:GHS_UCDB_THEME_GENERAL_CHARACTERISTICS_GLOBE_R2024A -where \"GC_UCN_MAI_2025='YOUR CITY' AND GC_CNT_GAD_2025='YOUR COUNTRY'\""
```

Note that the city name and country are both matched.  Many city names recur around the world, so querying on the name alone can select the wrong urban centre, or several at once.  Opening the database in a desktop GIS such as QGIS and browsing the `GC_UCN_MAI_2025` and `GC_CNT_GAD_2025` attributes is the most reliable way to find the values for your city.

*Configuring an urban centre this way replaces the earlier `urban_query` parameter, which is deprecated.*


Destinations, open space, blue space and sample point locations may also be supplied from your own data, to supplement or replace what is otherwise derived from OpenStreetMap.  These are configured under `points_of_interest`, `areas_of_interest` and `sampling` respectively; see [Custom data](https://healthysustainablecities.github.io/global-indicators/Custom-data).

As with every other dataset, store these wherever suits you and give the path relative to `process/data` — most simply, alongside the rest of your study region’s data.


The global indicators software has been designed to report on both policy and spatial indicator results.  Once the [policy checklist](https://github.com/healthysustainablecities/global-indicators/raw/refs/heads/main/process/data/policy_review/gohsc-policy-indicator-checklist.xlsx) has been completed for a city, save it wherever you keep that study region’s data and give its path in the `policy_review` setting.  Note that this one setting is resolved relative to the project root rather than to `process/data`, so the path includes the `process/data` prefix — as in the bundled example, `process/data/examples/ES_Las_Palmas_2025/policy/gohsc-policy-indicator-checklist-example-ES-Las-Palmas.xlsx`.  Using the GHSCI [web app](https://healthysustainablecities.github.io/global-indicators/#Web-app) interface you can then select a completed file to view, query and generate a PDF summary report.

Collections of General Transit Feed Specification (GTFS) feeds are used to represent public transport service frequency.  See the [GTFS reference](https://gtfs.org/schedule/reference/) for details on what is required for GTFS feeds.  More than one transit operator may operate in the region of interest, so it is important to aim to have full coverage of both the region and the operators, without overlap of services, to represent the service frequency of public transport stops in a city.

Transit feed data may be available from Government open data portals, or otherwise from aggregator sites such as https://transitfeeds.com/ and https://www.transit.land/.

Zipped feeds for a study region are kept together in one folder, named by the `folder` setting as a path relative to `process/data` — most simply, a `gtfs` folder alongside the rest of that region’s data, as in the bundled example.  A folder that is not found there is also looked for under the shared GTFS root (`transit_feeds` by default), so configurations written for earlier versions continue to work.  The folder and the feeds within it are configured in the region configuration file.  For example,

```yaml
## Optional set-up for General Transit Feed Specification (GTFS) transit data.
## GTFS feed data is used to evaluate access to public transport stops with regular weekday daytime service
## For cities with no GTFS feeds identified, this may be left commented out.
gtfs_feeds:
    ## Folder holding this region’s feeds, relative to process/data
    folder: examples/ES_Las_Palmas_2025/gtfs
    ## list of zipped GTFS feeds saved in the above folder
    gtfs_es_las_palmas_guaguas.zip:
        ## Name of agency that published this data
        gtfs_provider: Guaguas
        ## Year the data was published
        gtfs_year: 2025
        ## Source URL for the data
        gtfs_url: https://www.guaguas.com/transit/google_transit.zip
        ## The start date of a representative period for analysis
        ## (outside school holidays and extreme weather events), e.g. Spring/Summer
        ## for Northern Hemisphere: 20250405
        ## for Southern Hemisphere: 20251008
        start_date_mmdd: 20250405
        ## The end date of a representative period for analysis
        ## (outside school holidays and extreme weather events), e.g. Spring/Summer
        ## for Northern Hemisphere: 20250605
        ## for Southern Hemisphere: 20251205
        end_date_mmdd: 20250605
```

Some GTFS feeds don't adhere to the reference standard and some customisation is possible to accommodate the mapping of alternate `route_types` and `agency_id` values.  The defaults for these fields are set project-wide under `gtfs` in `process/configuration/config.yml` (initialised from [this template](https://github.com/healthysustainablecities/global-indicators/blob/main/process/configuration/templates/config.yml)), along with the headway table name, the analysis period and the folder GTFS feeds are looked for in.  A study region’s own `gtfs_feeds` settings take precedence over those, and an optional `datasets.yml`, if you have one, is consulted in between. These can be over-ridden for each mode, for example, for the below feed which describes service schedules for a [semi-Metro](https://en.wikipedia.org/wiki/M%C3%A1laga_Metro) a route type of 400 was used.  This was mapped as a value for the 'Tram' mode to allow analysis to progress:

```yaml
gtfs_feeds:
    folder: Marc issues/Malaga
    20230519_130136_Metro_Malaga:
      gtfs_provider: Metro de MÃ¡laga
      gtfs_year: 2023
      start_date_mmdd: 20230519
      end_date_mmdd: 20230831
      modes:
        Tram: {'route_types': [400]}
```

Multiple values can also be specified, e.g.,

```yaml
      modes:
        Bus: {'route_types': [700,712,714]}
```

However, in most cases, the `route_type` values for a feed (found in the `routes.txt` file) should correspond to the [defaults of the specification](https://gtfs.org/schedule/reference/#routestxt), in which case the `modes` parameter can be omitted as per the example configuration.  This will draw upon the default settings.
