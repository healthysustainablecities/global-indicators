# 5. Detailed Setup

Additional general information on configuration, analysis, reporting and comparison steps using the GHSCI software is provided below, including guidance on [what to do if you get stuck](https://healthysustainablecities.github.io/global-indicators/#What-if-I-get-stuck).

## Study regions
Before commencing analysis, your study regions will need to be configured with details of your downloaded data, the metadata used to document this data, and parameters to guide the software's usage of this data in analyses.

The configuration files are text files using the [YAML](https://yaml.org/) (.yml) format.  They can be opened and modified using a text editor to define region-specific details, including which datasets are being used, where they were sourced from, and how they should be interpreted.  Region configuration files may be located in either of two places: the `process/configuration/regions` sub-folder, or a `configuration` folder within a study region’s own data folder.  The second is the recommended pattern for new regions, because it keeps a city’s configuration and its data together and portable.  A codename must be unique across both locations — an ambiguous one is reported rather than guessed at.

An example region configuration for Las Palmas de Gran Canaria (for which data supporting analysis is included) has been provided in the file `process/data/examples/ES_Las_Palmas_2025/configuration/ES_Las_Palmas_2025.yml`.  This can also be viewed online [here](https://github.com/healthysustainablecities/global-indicators/blob/main/process/data/examples/ES_Las_Palmas_2025/configuration/ES_Las_Palmas_2025.yml).  At the top of the configuration file are some instructions that describe how to understand and modify the file.

[![image](https://github.com/user-attachments/assets/a4839430-2970-4aee-87fa-e86b9973925f)](https://youtu.be/W9iHHTBHC2s)

New regions can be added by using the `configuration` utility functions described elsewhere that initialise a new region configuration file using a city [codename](https://healthysustainablecities.github.io/global-indicators/#Codenames) at `process/configuration/regions/_codename_.yml`.  This file can be edited using a text editor, or within [Jupyter Lab](https://healthysustainablecities.github.io/global-indicators/#Jupyter-Lab).

**Study region template**

The blank template that is copied for every new study region is [`process/configuration/assets/region_template.yml`](https://github.com/healthysustainablecities/global-indicators/blob/main/process/configuration/assets/region_template.yml).  It is thoroughly commented: every parameter is preceded by a description of what it is for and how to complete it, and optional sections are marked out with lines of hash symbols so that they can be uncommented as needed.

Reading the template itself is the most reliable guide to configuration, because it is the file the software actually uses and is updated with it.  The optional sections it describes are covered in more detail on their own pages:

- [Custom aggregation](https://healthysustainablecities.github.io/global-indicators/Custom-aggregation) — `custom_aggregations`, for summarising results for your own areas of interest
- [Custom data](https://healthysustainablecities.github.io/global-indicators/Custom-data) — `points_of_interest`, `areas_of_interest` and `sampling`, for supplying your own destinations, open space, blue space and sample points
- [Earth Engine indicators](https://healthysustainablecities.github.io/global-indicators/Earth-Engine-indicators) — `gee`, for the optional green space and urban heat indicators

**Example configuration for Las Palmas de Gran Canaria (Spain) in 2025**

A completed configuration is provided for the example study region, with data included so that it can be run as-is: [`ES_Las_Palmas_2025.yml`](https://github.com/healthysustainablecities/global-indicators/blob/main/process/data/examples/ES_Las_Palmas_2025/configuration/ES_Las_Palmas_2025.yml).  Copying this file and modifying the values is often the easiest way to start configuring a new region.

An Earth Engine variant is also provided as [`ES_Las_Palmas_2025-ee.yml`](https://github.com/healthysustainablecities/global-indicators/blob/main/process/data/examples/ES_Las_Palmas_2025/configuration/ES_Las_Palmas_2025-ee.yml), which differs only in setting `gee: true` and using the `spatial_ee` and `policy_spatial_ee` report templates.

The whole of [`process/data/examples/ES_Las_Palmas_2025/`](https://github.com/healthysustainablecities/global-indicators/tree/main/process/data/examples/ES_Las_Palmas_2025) is worth browsing: it holds the configuration, every input dataset, the licences for each of them, and `scripts/prepare_example_data.py`, which regenerates each excerpt from its source.  It is the working model for what a self-contained study region folder looks like.

The earlier example, `example_ES_Las_Palmas_2023`, is retired.  Loading that codename reports its replacement rather than offering to initialise a new region; where its configuration file is still present the region still loads, so earlier results can be compared with current ones.

## Codenames
Region configuration files are named using a codename to represent a city when used in processing, for example `ES_Las_Palmas_2025`.  This helps to avoid issues with ambiguity when analysing multiple cities across different regions and time points (e.g. cities named Valencia are found in both Spain and Venezuala). In the case of our example city, 'ES' clarifies that this is a Spanish city, 'Las_Palmas' is a common short way of writing the city's name, and the analysis is designed to target 2025, using data sources that could be reasonably assumed to provide a fair representation for the city at that time point.

That a study region is a worked example distributed with the software is recorded by the configuration setting `example: true`, rather than by its name; reports generated for it are marked as demonstrations.  Your own regions should not set it. 

## Initialising

To initialise a new study region configuration file, you can run use the [Web app]() study region form, [Jupyter Lab](https://healthysustainablecities.github.io/global-indicators/#Jupyter-Lab) or Python (see example below), or command line (`configure <codename>`; Figure 17).  Running the configuration step for a study region with a previously initialised configuration file (e.g. `configure ES_Las_Palmas_2025`) would advise that the study region configuration has already been initialised, and provide guidance on how to run analyses once configuration has been completed by the user using a text editor.  

![image](https://github.com/user-attachments/assets/a461cba9-c400-4275-a3fc-b2436517a578)   
*Figure 17. Output resulting from creating the configuration files; if you were to run this a second time after successfully running it, it would recognise and report that the files already exist, and otherwise remind you about the purpose of the respective configuration files.*

Alternatively, you can initialise a configuration file using Python (including using a Jupyter notebook), for example for the Australian city of Melbourne with a target time point of 2023:
```
from subprocesses import ghsci
r = ghsci.Region('AU_Melbourne_2023')
```

Once initialised, study region configuration files must then be modified using a text editor to provide information on the locations of downloaded data and analysis parameters as required.   

*A good way to view and edit the configuration files is using the provided [Jupyter Lab](https://healthysustainablecities.github.io/global-indicators/#Jupyter-Lab) interface.*

*Other than initialising a new study region (as described above), you can also copy the provided example to a new file and modify the values as required; this might be the easiest way to get started with your new region!*

## Advanced options

Additional configuration files will be initialised in the `process/configuration` folder, and may be be edited in a text editor (or in a spreadsheet editor such as Excel for the CSV file) to add and customise analysis for new regions, including

- `config.yml` for overall project configuration, including the names of you, your colleagues and organsisation for inclusion in generated metadata and reports
- `config.yml` also carries the project-wide defaults for the pedestrian network query (`network_analysis`) and for GTFS analysis (`gtfs`: the headway table name, analysis period, route type mapping and data folder), which a study region may override individually
- `datasets.yml` is optional and no longer provided as a template.  If you create one, it can define shared datasets and metadata for OpenStreetMap, population, urban regions and transit feeds that are referenced by name from multiple study regions.  Settings resolve through a study region’s own configuration first, then `datasets.yml`, then `config.yml`, then the built-in defaults

Optionally, projects can be configured to:

- analyse [GTFS feed data](https://database.mobilitydata.org/) for evaluating accessibility to regularly serviced public transport
- use custom sets of OpenStreetMap tags for identifying destinations (see [OpenStreetMap TagInfo](https://taginfo.openstreetmap.org/) and region-specific tagging guidelines to inform relevant synonyms for points of interest)
- use custom destination, open space, blue space and sample point data (see [Custom data](https://healthysustainablecities.github.io/global-indicators/Custom-data))
- exclude an area from the study region and its buffer with `exclusion_region` — for example a neighbouring country that must not enter network or accessibility calculations.  It takes a boundary the same way any other dataset does, including layer selection and a `-where` filter, and its geometry is subtracted from both the urban study region and the buffered study region after they are created
- choose the [routing engine](https://healthysustainablecities.github.io/global-indicators/7.-Advanced-Features#routing-engine) used for the pedestrian accessibility calculations

| Configuration file   | File description                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
|----------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **regions/_codename_.yml**      | Used to define and specify details for study regions to be analysed.  ** Generate this file by running the configuration script followed by a codename of your choice, then open and edit the resulting text file guided by the provided headings.**|
| config.yml           | Defines general project parameters (e.g. your name and local time zone, for accurate localised recording of start and end times of processing in log files).|
| osm_open_space.yml   | Definitions for identifying areas of open space using OpenStreetMap |
| datasets.yml         | Optional and no longer provided as a template; may be created to define shared datasets and their associated metadata, referenced by name from multiple study regions |
| indicators.yml       | Some aspects of indicators calculated can optionally be modified here; currently this is set up for the core indicators of interest for the  [1000 City Challenge](https://www.healthysustainablecities.org/1000cities). | 
| osm_destinations.csv | Used to classify destinations to be retrieved from OpenStreetMap and support calculation of indicators defined in indicators.yml (e.g. percentage of population with access to a particular kind of amenity) | 
| policies.yml         | A list of policies for reporting.  This is a proof of concept for now, based on the 25-city comparative study.  An update is planned to support the new policy template.|
